# DeepSeek Notes 设计规范 v2

面向密集型中文桌面知识工具。所有数值均为规定值，不是建议值。

> 本规范的参照对象是一套 Apple 风格设计系统，但只继承其**设计主张**，不使用其任何代码、色值或组件。
> 凡与"密集型工具"冲突的主张，本规范一律以密度优先，并在相应位置说明取舍理由。

**v2 修订说明**：v1 经三份深度代码审计（对话区 / 笔记本 / 主题基础设施）核对后发现多处与实现不符或自相矛盾，
本版逐条修正。主要更正：AI 回复不是气泡而是全宽文档流（§10）；密度层定义与硬上限打架（§2）；
会话侧栏验收数字算错（§2.2）；排版章节缺作用域声明导致与 13 套 Markdown 主题冲突（§4.0）；
补充流式输出、分段控件、toggle chip、下拉浮层、分栏布局、用户自定义色标等缺失条目。
凡本版新增或更正处标 **[v2]**。

## 1. 设计原则

六条。前五条继承自参照系统，第六条是我们特有的、且**优先级最高**的约束。

1. **边框优先于阴影。** 静止态用 1px 描边定义边界，阴影只用于 hover、拖拽、浮层。
2. **留白代替分隔线。** 分组靠间距，不靠 divider。仅在密集列表中（§2）保留分隔线。
3. **层级靠字号跨度，不靠颜色。** 颜色不参与信息层级表达。
4. **主色是稀缺资源。** 整页先是黑白灰，主色只标记"当前要点击的那一个"。
5. **需要竖向对比的数字用等宽。**
6. **密度优先于呼吸感。** 与前五条冲突时，本条胜出。参照系统服务于一屏一件商品的营销页；我们的用户要同时看侧栏、消息流、列表和编辑器。**降低可视信息量是功能倒退，不是设计升级。**

## 2. 密度分层（核心模型）

界面分三层。**每个区域必须明确归属一层**，不允许"看情况"。

| 层级 | 单行元素高 | 内边距 | 正文字号 | 分隔方式 | 适用 |
|---|---|---|---|---|---|
| **紧凑** Compact | 24–36px | `6px 8px` | 12–13px | 允许 1px 分隔线 | 扫描/比对区 |
| **标准** Standard | 32–40px | `8px 12px` | 14px | 间距分组 | 操作区 |
| **宽松** Comfortable | — | `24–32px` | 15–16px | 仅间距 | 阅读/展示区 |

**[v2]** v1 把紧凑层定义成"行高 28–36px"，却在 §2.1 给出 56/64/84px 的硬上限，两者自相矛盾。

修正的关键是认清：**多行行项的高度取决于内容有几行，无法在层级表里统一设限**
（会话项两行、技能项三行，都属紧凑层却必然不等高）。因此本表只规定
**单行元素**（按钮、chip、工具调用行、分段控件）的高度区间；
**多行行项的上限一律由 §2.1 逐条规定**，本表不设统一上限。

两条附加约束：

- 同一列表内所有行**必须等高**（含行内编辑态，见 §10 列表行）
- §2.1 的逐条上限按**验收目标**（§2.2 的一屏条数）倒推，不按现状照抄

### 2.2 验收标准 **[v2 全面重算]**

v1 的数字是估算的，实测后不成立，本版按实测重定，并**补齐最小窗口 960×600 的标准**——
密度崩塌恰恰发生在最小窗口，只定 1280×800 拦不住。

实测基线（浏览器真实渲染，非估算）：会话侧栏行高 **53.75px**，`space-y-0.5` 后步距 **55.75px**，
头部 **96.67px**，列表可用高度 **631.33px** → 当前一屏仅 **11.32** 条。
（v1 写"≥12 条"且允许行高放宽到 56px，两条数学上无法同时成立：12 × 56 = 672 > 631。
根因是把 `text-[11px]` 的行高按 1.2 倍估算，实测计算值为 **16.5px**，即 1.5 倍。）

| 区域 | 1280×800 | 960×600 |
|---|---|---|
| 会话侧栏 | ≥ **12** 条 | ≥ **8** 条 |
| 笔记列表 | ≥ **12** 条 | ≥ **8** 条 |
| 笔记网格 | ≥ **9** 张 | ≥ **6** 张 |
| 全局搜索结果 | ≥ **8** 条 | ≥ **5** 条 |
| 内置插件 | 7 行 + 分区标题无滚动同屏 | 允许滚动 |

**达成路径（每条都由实测可用高度倒推，不是拍脑袋）：**

| 区域 | 实测可用高 | 现状 | 达标所需 | 达标后 |
|---|---|---|---|---|
| 会话侧栏 | 631px（头部 96.67px） | 步距 55.75px → 11.3 条 | 行高 ≤48、头部 ≤80 → 可用 648、步距 50 | **12.9 / 8.9 条** |
| 笔记列表 | 630px @1280×800｜430px @960×600 | 节距 70px → 9 条 | 行 ≤51px + 1px 分隔线 = 节距 52px，**取消 6px 行间距** | **12.1 / 8.3 条** |
| 笔记网格 | 同上 | 节距 185px → 9 张 / 4 张 | 卡片 ≤128px，节距 ≤140px | **13 / 6 张** |

笔记网格现状有个反常识的事实：**网格视图（9 张）与列表视图（9 条）密度完全相同**，
网格没换来任何密度收益，却牺牲了标题完整度。压到 128px 后网格才真正体现优势。

**[v2] 补充约束（重算）**：最小窗口 960×600 下，顶栏 + 输入区占用 ≤ **28%**。

v1 写 25%，但与 §10「多行输入最小 3 行」在算术上不可能同时成立。实测最小构成：

| 构件 | 高度 |
|---|---|
| 拖拽把手 | 20 |
| 工具栏 | 24 |
| textarea（2 行 × 22.4） | 44.8 |
| 内边距 + 边框 | 17 |
| **小计** | **105.8** |
| + 顶栏 56 | **161.8 = 27.0%** |

3 行时为 30.7%，超标。故规定：**窗口高度 < 700px 时最小行数降为 2 行**，
预算定 28%（2 行构成留 1 个百分点余量）。这比"钳制高度"更具体——
v1 只说"高度须随视口钳制"，却没说钳到哪，实现者无从下手。

### 2.3 点击热区

桌面应用，非移动端。**不采用参照系统的 44×44pt**。

- 独立按钮：≥ 32×32px
- 工具栏/列表内图标按钮：≥ 24×24px（图标 16px + 4px 内边距）
- 列表行整行可点：行高即热区
- 相邻可点元素间距 ≥ 4px

## 3. 色彩

### 3.1 架构：两层，深色只翻转语义层

```
第 1 层 Primitive  ── 纯色值，与主题无关，全局唯一真源
第 2 层 Semantic   ── :root（浅）与 .dark（深）只重新映射角色 → primitive
```

**硬约束（两条，缺一不可）[v2]**：

1. `.dark` 中不得重新定义任何 primitive。深色模式只允许改变语义层的指向。
2. **语义层不得直接书写字面色值。** 任何新色必须先升为 primitive 再被引用。

v1 只写了第 1 条，结果 `tokens.css` 自己用第二种方式绕过了约束（`--c-subtle: 16 16 19` 直接写字面值），
而同一文件对另外两个补色却规规矩矩升成了 primitive。已修正为 `--p-zinc-925` / `--p-zinc-875`。
这两条合起来才能保证"改一次品牌色，两套主题同时生效"。

### 3.2 中性色：统一用 zinc

**决策：全项目统一 `zinc`，废弃 `gray`。**

理由：应用根节点 (`App.vue`) 与对话区已是 zinc，对话区是使用频率最高的主界面；gray 在 Tailwind 中偏冷带蓝，与蓝色主色叠加后深色模式浮层明显偏蓝（现状 `dark:bg-gray-900` 浮层盖在 `dark:bg-zinc-950` 根节点上即为此问题）。

### 3.4 三条必须遵守的色彩规则

1. **控件边框比分隔线边框深一档**（浅色 `#8e8e97` vs `#e4e4e7`）。输入框边框要比卡片边框更实，因为它暗示"可编辑"。
2. **深色模式主色提亮一档**（`#2563eb` → `#60a5fa`）。同一支蓝在深底上会显暗，不提亮会掉到 4.5:1 以下。
3. **侧栏用「底色差异 + 1px 分隔线」双重分离** **[v2 更正]**。
   v1 照搬参照系统的主张写成"靠底色差异分离，不靠竖线"，实测后不成立：
   浅色 `#ffffff → #fafafa` 明度比仅 **1.038**，深色 `#09090b → #101013` 仅 **1.047**，
   两种模式下都低到几乎不可辨。底色差异只能提供"区域感"，边界仍须由 1px 线承担。
   这与 §1 原则 1「边框优先于阴影」一致，代价也只有 1px。

### 3.4.1 相邻表面的明度差 **[v2]**

§6.3 规定"深色模式下层级靠表面提亮表达"，但 v1 没有给出最小明度差，规则无法验收。实测：

| 关系 | 类型 | 明度比 |
|---|---|---|
| canvas `#09090b` → subtle `#101013` | 并列区域（侧栏） | **1.047:1** |
| canvas `#09090b` → surface `#18181b` | 堆叠层（卡片） | **1.123:1** |
| surface `#18181b` → raised `#27272a` | 堆叠层（浮层） | **1.189:1** |

三个数值都很小，结论是**深色模式下表面色不足以独立表达层级**。规定：

- **堆叠层**（卡片、浮层）：明度比 ≥ **1.1:1**，且**必须同时有 1px 边框**，不得只靠表面提亮。
  **[v2] 边框色不得与它所描的表面同色**：初版深色 `--c-border` 与 `--c-raised` 同为 zinc-800，
  对比度 **1.000**，浮层边框完全不可见，这条规则在深色下空转。已改为 zinc-700
  （在 canvas/surface/raised 上分别为 1.91 / 1.70 / 1.43，是唯一三者皆可见的取值）。
- **交互反馈（hover / active）不使用固定灰阶**：深色下 `--c-muted` 叠在 `--c-surface` 上仅 **1.042**，
  几乎不可见，且在浮层上方向会翻转。改用前景色半透明叠加（`--c-hover` 6% / `--c-active` 10%），
  在明暗两态、所有表面上稳定给出 **1.13–1.20**
- **并列区域**（侧栏 vs 内容区）：明度比 ≥ **1.04:1** 即可，但**必须有 1px 分隔线**
  （区域相邻边很长，大面积微差可提供区域感，但边界须由线承担 —— 见 §3.4 第 3 条）
- 浮层额外叠加 `--shadow-overlay`，尽管深色下阴影贡献有限
- **不得**用提高表面明度的方式来替代边框：继续提亮会让深色模式整体发灰，失去深色的意义

### 3.5 无障碍说明（诚实披露）

- **正文全部达到 WCAG AA 4.5:1**，功能色亦然。
- **禁用态**不受 WCAG 1.4.3 约束，故 `--c-text-disabled` 允许低于 4.5:1。
- **装饰性分隔线**不受 1.4.11 约束。
- **深色模式的控件边框（2.29:1）达不到 1.4.11 的 3:1。** 这是深色 UI 的普遍取舍——要达标需把边框提亮到 `#8e8e97` 级别，视觉上会过重。我们的处理：控件的可识别性由**填充底色 + 标签**承担，无障碍要求由**焦点指示器**承担（深色下 6.97:1，远超 3:1）。这是有意的取舍，不是疏漏。

### 3.6 主色使用纪律

一屏之内，主色只能出现在**唯一的主行动**上。以下场景**禁止**使用主色：

- 分区标题的装饰图标（现状 Profile 有 8 处彩色图标标题 → 改为中性色）
- 状态徽章（改用中性色 + 文字，仅错误/成功可用功能色）
- 选中态（用 `--c-muted` 底 + `--c-text` 文字，不用主色填充）
- 多个并列按钮同时用主色

现状问题：`focus:ring` 出现了 8 种颜色（blue/purple/indigo/emerald/rose/orange/violet/cyan）。**焦点环永远是主色，不随功能变色**（§7.2）。

### 3.7 用户自定义色标 **[v2]**

笔记颜色（6 色）与标签颜色（8 色）是**用户数据**，不受 §3.6 的主色纪律约束，但必须有可读性护栏。
这是笔记本区最严重的可读性缺陷来源：现状标签色被直接内联到 `color` 与 `background`，
实测对比度 **1.43–1.63:1**，选中态白字更低至 **1.53:1**，而色值来自随机取色，没有任何护栏。

规定：

1. **用户色标默认只作为色块、圆点或指示条**，面积不超过 16×16px，**不承载文字**。
2. 若必须承载文字（如标签胶囊），前景色**按底色明度自动切换**黑/白，并保证 ≥ **4.5:1**。
   底色须先按主题调整明度：浅色模式用色相的浅色调 + 深色文字，深色模式反之。
3. 取色不得随机。提供固定的 8 色调色板，每色预先给出「浅底/浅底前景/深底/深底前景」四个值，
   全部经对比度校验后写入 token 层。
4. 色标仅表达分类，**不表达状态或层级**——状态用 §3.3 的功能色。

## 4. 排版

### 4.0 作用域：应用主题 vs 内容主题 **[v2]**

这是 v1 最大的空白。项目里有**两套并行的视觉体系**，v1 没有声明边界，导致 §4 与 13 套 Markdown
主题大面积冲突且无法判定谁对（例：§4.2 规定"字重只用 400/500/600，禁用 700 及以上"，
而主题里 business/technical/social/wechat 的 h1/h2 用 700，magazine 用到 900）。

| | 应用主题（App Chrome） | 内容主题（Content Theme） |
|---|---|---|
| 范围 | 界面外壳：导航、侧栏、列表、表单、弹窗、按钮 | Markdown 渲染结果：预览区、导出产物 |
| 归谁管 | **本规范 §3–§10 全部条款** | `markdown-themes/`，13 套主题各自定义 |
| 明暗 | 跟随应用主题 | 由主题自身声明；`academic` 仅浅色、`darkcode` 仅深色 |
| 字重 | 400 / 500 / 600 | **不受限**，排版表现力优先 |
| 字号 | §4.2 的 10 档 | 主题自定义（实测 8 套正文 ≥16.5px） |

**边界规则：**

1. §4.2 字号档、§4.3 中文排版规则、§3 色彩 token **只约束应用主题**。
2. 内容主题**必须**满足的仅三条：正文对比度 ≥4.5:1；不得依赖需联网加载的字体（§4.1）；
   容器内文字可选中复制。
3. **主题的明暗不得挂在应用的 `.dark` 类上。** 现状 `gen-themes.js` 把主题深色变体挂在应用 `.dark` 上，
   导致：用户选的主题只决定色系不决定明暗；`academic`（仅浅色）与 `darkcode`（仅深色）
   在相反的应用主题下变成刺眼反色板。主题应自带明暗声明，与应用主题解耦。
4. 分栏编辑模式下，编辑区属应用主题（14px），预览区属内容主题（16.5–24px），
   **同屏两种密度是预期行为**，不是缺陷。

### 4.1 字体：先修一个真实存在的缺陷

**问题 1：Google Fonts 从未加载成功。**

`src/assets/markdown-themes/index.css:4` 从 `fonts.googleapis.com` 加载 13 个字族（其中 `JetBrains Mono` 在主题中被引用 **51 次**）。但 `src/index.html` 的 CSP 是：

```
default-src 'self'; style-src 'self' 'unsafe-inline'
```

`style-src` 不含 googleapis，且 **`font-src` 未声明**（回落到 `default-src 'self'`）。跨域样式表与字体文件双双被拦截。

实测确认（开发环境，Chromium）：`document.styleSheets` 中无 googleapis 条目，`document.fonts` 注册的 FontFace **数量为 0**；按渲染宽度测量，`JetBrains Mono` / `Inter` / `Lora` 的宽度与通用兜底字体**完全相同**，即全部回落。

**结论：13 套 Markdown 主题的排版意图从未实现过。** 且对中文用户，`fonts.googleapis.com` 通常不可达，即使放开 CSP 也不可靠。

**规定：移除该 `@import`。** 主题排版改为基于本机字体设计。若确需特定字族，必须**本地打包**（`@font-face` + 本地 woff2）并在 CSP 增加 `font-src 'self'`——这是唯一符合"数据完全本地"产品定位的做法。

**问题 2：Windows 上英文和数字用了中文字体渲染。**

现状字体栈：

```
-apple-system, BlinkMacSystemFont, 'PingFang SC', 'Hiragino Sans GB', 'Microsoft YaHei', 'Segoe UI', sans-serif
```

字体回退是**逐字形**进行的。在 Windows 上 `-apple-system` / `BlinkMacSystemFont` / `PingFang SC` / `Hiragino Sans GB` 全部不存在（实测确认），于是 **`Microsoft YaHei` 同时承担了拉丁字母和汉字**，而排在其后的 `Segoe UI` 永远不会被使用。YaHei 的拉丁字形质量明显弱于 Segoe UI。

**规定：拉丁字体必须排在 CJK 字体之前。**

```css
--font-sans: -apple-system, BlinkMacSystemFont, 'Segoe UI', 'PingFang SC',
             'Microsoft YaHei UI', 'Microsoft YaHei', system-ui, sans-serif;
```

- macOS：`-apple-system`(拉丁) → `PingFang SC`(汉字)
- Windows：`Segoe UI`(拉丁) → `Microsoft YaHei UI`(汉字)

**等宽字体**（全部本机可用，实测确认；移除未安装的 JetBrains Mono / Fira Code）：

```css
--font-mono: 'Cascadia Code', 'Cascadia Mono', Consolas, 'SF Mono', Menlo, monospace;
```

### 4.2 字号梯度

现状 93% 的文字挤在 12/14px 两档。新梯度共 10 档，**但不照搬营销页的 80px hero**——那服务于"一屏一句话"，与本工具无关。

**[v2]** 全部字距为 **0**：本应用标题以中文为主，负字距会让方块字相互侵入（§4.3）。
拉丁文为主的大字如需收紧，另加 `.tracking-latin`（-0.02em）工具类，**禁止用于中文**。
"可用层级"列已按 §2 的密度定义收紧——把 `body`/`title-3` 标为"全部"会与紧凑层的 12–13px 冲突。

| Token | 字号 | 字重 | 行高 | 用途 | 可用层级 |
|---|---|---|---|---|---|
| `metric` **[v2]** | 40px | 600 | 1.1 | 统计卡数字、OCR 百分比（必配 `tabular-nums`） | 仅宽松 |
| `display` | 32px | 600 | 1.2 | Help 章节标题、Onboarding 标题 | 仅宽松 |
| `title-1` | 24px | 600 | 1.3 | 页面主标题 | 宽松 |
| `title-2` | 20px | 600 | 1.35 | 分区标题、空状态主标题 | 标准/宽松 |
| `title-3` | 16px | 600 | 1.5 | 卡片标题、弹窗标题 | 标准/宽松 |
| `body-lg` | 15px | 400 | **1.7** | Help 正文、编辑器正文 | 标准/宽松 |
| `body` | 14px | 400 | **1.6** | 默认正文、表单 | 标准/宽松 |
| `body-sm` | 13px | 400 | 1.55 | 列表主行、密集正文 | 紧凑/标准 |
| `label` | 12px | 500 | 1.4 | UI 标签、按钮文字、列表标题 | 全部 |
| `caption` | 11px | 400 | 1.4 | 元信息、时间戳、计数 | 全部 |
| `mono` | 13px | 400 | 1.5 | 代码、Token、路径 | 全部 |

**[v2]** `metric` 40px 是 §2.1 统计卡与 OCR 进度所要求的值。它超出 §4.2 其余档位，
理由是**它渲染的是数字不是文本**——数字无字形复杂度，大字号不构成阅读负担，
且并排比较时字号本身就是"这是关键指标"的信号。这不是营销页式的大字。

字重只用 **400 / 500 / 600** 三档。禁用 700 及以上——层级由字号跨度承担（32 ÷ 11 ≈ 2.9 倍），不由字重承担。

### 4.3 中文排版专项

这一节的规则**优先于**参照系统的任何排版主张。

1. **字号 token 一律不含负字距** **[v2 更正]**。
   汉字是等宽方块字，负字距会让字面相互侵入，20px 以下尤其明显。参照系统的 `-0.022em` 正文字距是为 SF Pro 拉丁文设计的，**不适用于中文**。
   v1 把负字距烤进了 `display`/`title-1` 两档，同时又规定"负字距只允许拉丁文"，
   而 §2.1 恰好指定这两档用于中文标题、§12.3 又验收"中文无负字距"——三者形成死循环，
   照规范用 token 就必然违规。现改为：token 不带字距，拉丁文大字另加 `.tracking-latin`。

2. **行高比拉丁文更大。** 中文无小写字母和升降部，视觉重心满格，行距不足会显得拥挤。正文行高 ≥ **1.6**，长文阅读区 ≥ **1.7**。这是本规范中唯一"比参照系统更宽松"的地方，且理由是可读性而非美学。

3. **禁止对中文使用 `uppercase`。**
   现状：`uppercase tracking-wider` 被用在「数据概览」「近 7 日活跃」「界面偏好」「笔记 (12)」「全局」等**至少 15 处中文标题**上（全项目 `tracking-wider` 17 次基本都是这个模式的复制粘贴）。`uppercase` 对 CJK 完全无效，而 `tracking-wider` 会把汉字间距拉散，形成"字与字之间漏风"的观感。
   **规定：中文分区标题使用 `label` 12px/500 + `--c-text-tertiary`，不加 `uppercase`，不加字距。**

4. **中英混排**：不插入额外间距。依赖字体自身的度量，避免用 JS 或 `::after` 注入空格——会破坏文本选择与复制。

### 4.4 等宽数字

需要**竖向对比或频繁变动**的数字必须加 `font-variant-numeric: tabular-nums`：

- 统计卡的四个数字、余额金额
- Token 计数、KV Cache 命中数
- 列表中的日期、计数徽章（如「笔记 (12)」）
- OCR 进度百分比
- 快捷键键帽

**不要给整个界面加 `tabular-nums`**——它会让正文中的数字变宽变丑。现状全项目仅 3 处使用，属明显不足。

## 5. 间距

基数 **2px**，主档 **4px 步进** **[v2]**。

档位：`2 / 4 / 6 / 8 / 12 / 16 / 20 / 24 / 32 / 48 / 64`

**[v2]** v1 的档位表是 `4/8/12/16/24/32/48/64` 却同时在场景表里写"图标与文字 4 或 6"，
自相矛盾；且实现中 6px 与 20px 高频出现（`gap-1.5`、`py-1.5`、`px-5`）都是合理的紧凑值。
本版把 2/6/20 纳入档位——密集界面需要比 4px 更细的调节粒度，硬砍会逼出更多任意值。

禁止使用档位外的值（现状 `top-[72px]` 等任意值须改用 token，见 §10 Toast）。

| 场景 | 值 |
|---|---|
| 图标与文字 | 4 或 6 |
| 行内元素间 | 8 |
| 表单控件内边距 **[v2]** | `4px 12px`（标准）/ `3px 10px`（紧凑）——见 §10 输入框的高度拆解 |
| 卡片内边距（紧凑/标准/宽松） | 12 / 16 / 24 |
| 列表项间距 | 0（用分隔线）或 4 |
| 分区间距（紧凑/标准/宽松） | 16 / 24 / 48 |
| 弹窗内边距 | 24（统一，现状有 p-6/p-5/p-8/px-4 四种） |
| 页面边距 | 24 |

**"留白代替分隔线"的边界**：仅在**宽松层**成立。紧凑层的列表**必须保留 1px 分隔线**——在 12 条以上的密集列表里，纯靠间距分组会让扫描定位变困难，这是可读性问题，不是审美问题。

## 6. 圆角、边框、阴影、层级

### 6.1 圆角

现状四套并存且无规则。**规定按组件类别取值**：

| 类别 | 值 | Tailwind |
|---|---|---|
| 按钮、输入框、选择器、标签 | **8px** | `rounded-lg` |
| 卡片、列表行、消息气泡 | **12px** | `rounded-xl` |
| **下拉浮层、气泡** **[v2]** | **12px** | `rounded-xl` |
| 弹窗、浮层面板 | **16px** | `rounded-2xl` |
| **嵌套元素**（如分段控件的选中项） **[v2]** | 外层 − 2px | — |
| 徽章、开关、头像、纯图标圆钮 | 全圆 | `rounded-full` |
| 媒体、代码块 | 8px | `rounded-lg` |

不采用参照系统的 `1.2rem`(19.2px) 全局圆角——那是为大尺寸营销卡片设计的，用在 32px 高的控件上会显得臃肿。也**不采用"按钮全胶囊"**：胶囊按钮在密集工具栏里会让相邻按钮的间距判断变困难。

### 6.2 边框

- 宽度恒为 **1px**。不使用 2px 边框（焦点环除外）。
- 分隔线用 `--c-border`；输入框等控件边界用 `--c-border-control`。
- **父容器的边框不得弱于子元素**。现状 Profile 深色下外层 section 用 `border-gray-800`（几乎不可见）而内层卡片用 `border-gray-700`（更亮），层级倒置，须修正。

### 6.3 阴影

**静止态不用阴影。** 现状 `shadow-2xl` 用了 13 次是最主要的违规。

| 层级 | 浅色 | 深色 |
|---|---|---|
| rest | 无（用边框） | 无（用边框） |
| raised（hover、下拉） | `0 2px 8px -2px rgb(0 0 0 / .08)` | `0 2px 8px -2px rgb(0 0 0 / .5)` |
| overlay（弹窗） | `0 12px 32px -8px rgb(0 0 0 / .16)` | `0 12px 32px -8px rgb(0 0 0 / .6)` |

**深色模式下阴影几乎不可见**，层级主要靠**表面提亮**表达：`canvas #09090b` → `surface #18181b` → `raised #27272a`。这是深色 UI 与浅色 UI 的根本差异，必须显式处理。

### 6.4 层级 z-index

现状三档随意取值，Toast 与快捷键弹窗同为 `z-[200]`，而破坏性确认弹窗反而最低（`z-50`）。**规定固定阶梯**：

| 值 | 用途 |
|---|---|
| 0 | 内容 |
| 10 | 面板内吸顶（分组标题等） |
| 20 | 下拉、气泡 |
| 30 | 抽屉、侧滑面板 |
| 40 | 遮罩 |
| 50 | 弹窗 |
| 60 | **确认/破坏性弹窗**（必须高于普通弹窗） |
| 70 | Toast |
| 80 | Tooltip |

### 6.5 遮罩

**统一一档**：浅色 `rgb(0 0 0 / .5)`，深色 `rgb(0 0 0 / .6)`，一律配 `backdrop-blur-sm`。现状四档随意且有一处漏了模糊。

## 7. 状态与焦点

### 7.1 状态表

每个可交互组件必须实现全部状态。现状外壳层 8 个文件焦点态为 0。

| 状态 | 表现 |
|---|---|
| default | 边框 + 表面色 |
| hover | 叠加 `--c-hover`（前景色 6% 半透明）；卡片可加 raised 阴影 |
| active | 叠加 `--c-active`（前景色 10%），**不位移**（现状有 `translateY` 位移，密集列表中会引起视觉抖动） |
| focus-visible | 见 §7.2 |
| disabled | `opacity: 0.4` + `cursor: not-allowed`（现状有 40/50/70 三档，统一为 **40**） |
| selected | `--c-muted` 底 + `--c-text` 文字 + 左侧 2px 主色指示条；**不整块填充主色** |
| loading | 保持原尺寸，内容替换为 spinner，**禁止改变布局** |

**[v2] 「禁止改变布局」适用于全部状态，不只 loading。** 任何状态切换
（hover / selected / expanded / 行内编辑）都不得改变元素占位尺寸。
最危险的实例：版本历史行在指针悬停时长高 25px，把下一行顶上来，
误点即触发**不可逆**的「恢复此版本」。规则：状态变化只允许改颜色、透明度、边框色，
需要显示额外内容时**必须预留占位**。

### 7.2 焦点

```css
outline: 2px solid var(--c-accent);
outline-offset: 2px;
```

三条硬规则：

1. **焦点环恒为主色**，不随功能变色。现状 8 种颜色须全部收敛。
2. **禁止 `outline: none` 而不补焦点样式**。现状 `GlobalSearch.vue` 的输入框写了 `outline-none` 却没补 ring，等于主动删除了键盘可达性。
3. 用 `:focus-visible` 而非 `:focus`，避免鼠标点击时出现焦点环。

焦点指示器承担了深色模式下控件可识别性的无障碍责任（§3.5），因此**不允许被移除或弱化**。

**[v2] 浮层的焦点管理适用范围。** v1 只把「焦点移入 / 归还」写在 §10「弹窗」条里，
而对话区有两个**非模态**浮层（Agent 下拉、笔记选择面板）不属于弹窗，形成键盘规则真空。规定：

| 浮层类型 | 焦点移入 | Esc 关闭 | 焦点归还 | 焦点陷阱 |
|---|---|---|---|---|
| 模态弹窗 | 必须 | 必须 | 必须 | 必须 |
| 非模态浮层（下拉、气泡） | 必须 | 必须 | 必须 | **不要** |
| Toast | 不移入 | — | — | 不要 |

### 7.3 热区豁免 **[v2]**

以下**连续型拖拽控件**豁免 §2.3 的最小热区要求，因为它们的操作是拖拽而非点击，
且加粗会侵占内容空间：滚动条（6px）、分栏拖拽条（4–8px）、输入区高度拖拽把手。
豁免的前提是：必须有 hover 态视觉反馈，且存在等效的键盘或菜单操作路径。

## 8. 动效

| Token | 时长 | 缓动变量 | Tailwind 类 | 用途 |
|---|---|---|---|---|
| `instant` | 120ms | `--ease-standard` | `duration-instant ease-out-soft` | 颜色、hover 反馈 |
| `fast` | 180ms | `--ease-standard` | `duration-fast ease-out-soft` | 下拉、开关、折叠 |
| `base` | 240ms | `--ease-standard` | `duration-base ease-out-soft` | 弹窗进入、页面切换 |
| `exit` | 160ms | `--ease-accelerate` | `duration-exit ease-in-soft` | 所有退出（退出快于进入） |

**[v2] 缓动变量刻意不叫 `--ease-out` / `--ease-in`。** 那两个名字既是 CSS 内置关键字、
也是 Tailwind 内置类名，而我们的曲线与它们完全不同——同名不同义会导致
「用错不报错，只是慢半拍」。v1 的表格里直接写了裸的 `ease-out`（CSS 内置曲线），
与 token 层的自定义曲线不是同一条。

现状：时长有 150/200/300/500 四档无标准；六个浮层里只有一个有进场动画，其余瞬时弹出；`App.vue` 定义的 `.page-enter/.page-leave` 是**死代码**（RouterView 未用 `<Transition>` 包裹）。

**必须实现降级**（现状全项目 0 处）。以下为 `tokens.css` 中的实际实现，
**加载指示器必须豁免**——把 spinner 冻成静止圆弧会让用户误判为卡死：

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
  /* 加载指示器是功能反馈而非装饰：放慢而不是停止 */
  [data-motion='loading'],
  [data-motion='loading']::before,
  [data-motion='loading']::after {
    animation-duration: 1.2s !important;
    animation-iteration-count: infinite !important;
  }
}
```

所有 spinner、流式等待三点跳必须标注 `data-motion="loading"`。

禁止：视差、弹跳缓动、超过 240ms 的进入动画、装饰性循环动画
（加载指示器不属"装饰性"，不受此限）。

## 10. 组件规范

统一约定：所有组件的圆角、间距、状态遵循 §5–§7，此处只列各自特有的规定。

### 按钮

| 变体 | 底 | 文字 | 边框 |
|---|---|---|---|
| primary | `--c-accent` | `--c-accent-fg` | 无 |
| secondary | 透明 | `--c-text` | `--c-border-control` |
| ghost | 透明 | `--c-text-secondary` | 无 |
| danger | `--c-danger` | 白 | 无 |

尺寸：`sm` 高 28px / 12px 字；`md` 高 32px / 14px 字（默认）；`lg` 高 40px / 14px 字。

现状问题：主操作按钮有三种圆角三种尺寸；次要按钮有"幽灵"与"描边"两种形态并存——统一为上表。

### 输入框 **[v2 更正]**

v1 写「高 32px + 内边距 `8px 12px`」，两者算术上不可能同时成立：
`1 + 8 + 22.4(body 14px/1.6) + 8 + 1 = 40.4px`。按**拆解式**规定，任一项改动都能立刻验算：

| 档 | 高度 | = 边框 | + 内边距 | + 行高 | + 内边距 | + 边框 |
|---|---|---|---|---|---|---|
| 标准 | **32px** | 1 | 4 | 22（`body` 14px/1.6） | 4 | 1 |
| 紧凑 | **28px** | 1 | 3 | 20（`body-sm` 13px/1.55） | 3 | 1 |

水平内边距 12px（紧凑 10px）——**呼吸感由水平内边距提供，不靠加高**。
圆角 8px，边框 `--c-border-control`，底 `--c-surface`。
现状 `rounded-xl px-3 py-2` 与 `rounded-lg px-3 py-1.5` 两级并存且无规则，统一按密度层选择。

### 列表行

紧凑层。左侧图标 16px + 12px 间距 + 内容区（标题 `label` 单行 truncate，副行 `caption`）+ 右侧操作区（hover 时显现）。
选中态用左侧 2px 主色指示条，不整块填充。

**[v2] 补充三条：**

- **图标位可选**。会话列表无图标是合理的（标题即标识），但同一列表内必须一致。
- **hover 操作区必须预留宽度**，不得用 `hidden group-hover:flex` —— 现状操作组出现瞬间挤压标题，
  truncate 位置跳变。改为常驻占位 + `opacity` 过渡。
- **[v2] 操作区在键盘聚焦时必须同样显形**（`:focus-within` 与 `:hover` 同等对待）。
  只挂 hover 会让列表操作成为纯鼠标专属功能，键盘用户无法触达。
- **行内编辑态与展示态必须等高**。现状编辑态（输入框 + 双按钮）与展示态（两行文本）高度不等，
  进入编辑时整个列表抖动。

### 用户消息气泡 **[v2 更正]**

右对齐胶囊。**底色用 `--c-muted`，不用饱和主色** —— 现状 `bg-blue-600` 白字整块填充，
违反 §3.6「主色只标记要点击的那一个」，而消息气泡不可点击。
圆角 12px，尾角 `rounded-tr-sm`（2px）形成方向指向 —— 这一非对称尾角是**允许的例外**，须显式声明。
最大宽度 `min(72%, 640px)`：v1 只写 720px 固定值，实现用 `max-w-[72%]` 百分比，
两者规则性质不同；取二者交集，既防超宽屏行长失控，也防窄窗口气泡占满。

必须补齐（现状缺失）：发送中 / 发送失败 / 重试 三态。现状消息 push 后即视为成功。

### AI 回复：文档流，不是气泡 **[v2 更正]**

**v1 在此处写错了。** 规范假定 AI 侧也是气泡（`--c-surface` 底 + 1px 边框 + 720px 上限），
而实现是**无底色、无边框、无内边距的全宽文档流**：左侧 32px 头像 + `flex-1` 正文列。
实测最宽行长可达 **1043px**。这是正确的形态选择（AI 回复常含标题、列表、代码块、表格，
气泡会限制这些块级元素的表现），规范应当承认它而不是改造它。

规定：

- 形态：左 32px 头像 + 正文列，**正文列无底色无边框**；头像不加阴影
- 正文 `body-lg` 15px / **行高 1.75**（长文阅读，高于 §4.2 的 1.7）
- **行长上限 `max-width: 640px`** **[v2 更正]**。初稿写 `72ch` 并括注"约 680–760px"，
  两处都不成立：`ch` 度量的是数字零的宽度，**在中文界面里不度量汉字**（1 个汉字 ≈ 2ch），
  且 72ch 在 15px 下实际约 590px，与括注差 15–30%。
  640px 在 15px 正文下约合 **42 个汉字/行**，落在中文长文的舒适区（30–45 字）内。
  用 px 而非 ch，正是因为中文的行长要按汉字数算，而 `ch` 做不到这件事。
- 内部块级元素（h1–h3、列表、引用、代码块、表格）的排版由**内容主题**接管（§4.0），
  但必须继承应用主题的色彩 token
- hover 动作条（存入笔记 / 复制）**必须预留占位高度**，否则流结束瞬间插入 33px 造成跳动

### 流式输出态 **[v2 新增]**

v1 完全没有这一节。§7.1 的 loading 是为按钮写的，对增量文本流无效。

| 规则 | 规定 |
|---|---|
| 滚动策略 | 默认吸底；用户上滑超过 **48px** 即解除吸底并显示「回到底部」按钮 |
| 布局稳定 | 动作条、产物卡的占位高度在流开始前就预留，禁止流结束时插入元素撑开布局 |
| 光标 | 末尾 1px 竖线，`--c-accent`，1s 闪烁；`prefers-reduced-motion` 下改为静态 |
| 未闭合语法 | 未闭合的 ``` 围栏、表格、链接按**纯文本**渲染，不得推测补全后再回退（会造成闪烁） |
| 组件连续性 | 工具调用组件在流结束时不得重建实例，展开状态须保留 |
| 等待态 | 三点跳动画属**功能反馈**，不受 §8「禁止装饰性循环动画」约束，须标 `data-motion="loading"` |

### 分段控件 Segmented control **[v2 新增]**

笔记本区有 3 处实例（网格/列表切换、编辑/分栏/预览切换），现状全部用 `bg-blue-500 text-white`
整块主色填充选中项。v1 没有此组件条目，实现者只能从「按钮」类推，
而按钮 primary **恰恰就是**主色填充 —— 类推的结果必然错。故必须显式规定：

- 容器：`--c-muted` 底，圆角 8px，内边距 2px
- 选中项：**`--c-raised` 底 + `--c-text` 文字 + `--shadow-raised`**，圆角 **6px**
- 未选中项：透明底 + `--c-text-secondary`
- **禁止用主色填充选中项**

**[v2 更正]** 初稿写选中项用 `--c-surface`，在深色下方向是反的：深色 `--c-muted`(#1c1c1f)
比 `--c-surface`(#18181b) **更亮**，选中项反而比容器更暗。改用 `--c-raised` 后
两种模式下选中项都比容器亮（浅色 #ffffff on #f4f4f5、深色 #27272a on #1c1c1f），语义一致。
6px 圆角是 §6.1 表格外的取值，因为它嵌套在 8px 容器内，须比容器小 2px 才不露角——**此为显式例外**。

### 可切换 chip（toggle chip） **[v2 新增]**

输入区工具栏的主体形态（引用笔记 / 附件 / 联网 / 展开 / Agent 共 5 枚）。v1 的「按钮」四变体
不含此形态，导致现状 4 枚并列 chip 用了 4 种颜色（blue / emerald / indigo / zinc），
直接违反 §3.6「多个并列按钮同时用主色」。

- 高 **24px**（§10 按钮三档不含此值，本形态单列一档），圆角 8px，12px 字 + 14px 图标
- 关闭态：透明底 + `--c-text-tertiary`
- **开启态：`--c-muted` 底 + `--c-text` 文字 + 1px `--c-border-control` 边框**，一律同色，不按功能分色
- 状态后缀（「·未配置」）用 `--c-text-tertiary`
- disabled：`opacity: 0.4` —— 现状 AgentSelector 的锁定态只改 `cursor`，视觉上与可用态完全相同

### 下拉浮层（非模态） **[v2 新增]**

Agent 选择器、笔记选择面板属此类。与「弹窗」不同：非模态、无遮罩、点外部关闭。

- `z-dropdown`（20），**不得与弹窗同层**（现状 Agent 下拉是 `z-50`，与弹窗撞层）
- 圆角 12px + 1px 边框 + `--shadow-overlay`
- 键盘规则（v1 只写在「弹窗」条里，非模态浮层无规可依）：
  `Esc` 关闭并把焦点归还触发器；`↑↓` 移动高亮；`Enter` 选中；`Tab` 关闭浮层并移到下一个控件
- 必须有 `role="listbox"` / `aria-expanded`
- 超过 12 项须提供搜索框
- 选中态遵循 §7.1（`--c-muted` 底），**同一列表内不得出现两种选中配色**（现状默认项用 zinc + blue 勾，Agent 项用 indigo + indigo 勾）

### 分栏 / 分屏布局 **[v2 新增]**

- 断点两侧须留 **≥15% 缓冲**，避免用户日常拖窗时反复跨越（现状阈值 1024px 恰在常用范围内）
- 每栏声明 `min-width`；断点值必须 ≥ 各栏 min-width 之和
- **跨断点必须保持组件实例**，禁止销毁重建 —— 现状跨 1024px 时编辑器被重建，新建笔记的未保存内容丢失
- 栏宽变化若要动画，须对 `width` 而非 `flex` 属性做过渡

### 多行输入 textarea **[v2 新增]**

对话区主输入是复合控件（可拖拽调高、记忆高度、全屏展开三态）。

- 最小 **3 行**；**窗口高度 < 700px 时降为 2 行** **[v2]**（见 §2.2 的预算推算）
- 最大高度 `min(40vh, 320px)`，超出滚动
- 高度**必须随视口钳制**，防止小窗口下输入区吃掉全部消息区
- 拖拽把手高 20px，属 §2.3 热区豁免项（连续型拖拽控件）
- 三态（常规 / 拖高 / 全屏）切换用 `fast` 时长

### 附件 chip **[v2 新增]**

- 图片态：64×64 缩略 + 右上 16px 删除钮；文件态：高 ≤32px 的 chip
- 状态：解析中（遮罩 + spinner）/ 就绪 / 错误。**错误必须在界面上可读**，
  不得只放进 `title` 属性（§11 要求「原因 + 下一步」）
- 角标（如「AI」视觉标识）遵循 §10 徽章规格，不得自定义 8px 字与 4px 圆角

### 产物卡片 **[v2 新增]**

消息流内与右抽屉内**必须共用一个组件**，现状是两个实现（图标尺寸、字号、圆角、
边框色、操作可见性全不同，数据却同源）。

- 紧凑层，步距 ≤52px；16px 图标 + 文件名 + 类型说明 + 操作区
- 操作区在消息流内常驻可见，在抽屉内 hover 显现 —— 这是**允许的差异**，须作为参数而非两套代码

### 工具调用气泡

紧凑层。折叠态单行 32px：emoji + 工具名 + 状态。展开显示参数与结果，代码用 `mono` 13px。
须与消息流同属 zinc 色系——现状此组件用 gray 而消息流用 zinc，是同屏色系冲突。

### 徽章

高 20px，`caption` 11px，圆角全圆，内边距 `2px 8px`。
默认中性（`--c-muted` 底 + `--c-text-secondary`），仅成功/警告/错误可用功能色。
现状三种尺度并存，统一为一种。

### 弹窗

圆角 16px，内边距 24px，**必须有 1px 边框**（现状一半靠 `shadow-2xl` 无边框），overlay 阴影，`base` 进入 / `exit` 退出动画。
统一支持：`Esc` 关闭、点遮罩关闭、`Teleport` 到 body、进入时焦点移入、关闭后焦点归还。
现状：确认弹窗未 Teleport、不支持点遮罩关闭、`Esc` 无反应。

### Toast

紧凑层。中性底 + 1px 边框 + 左侧 3px 功能色指示条，**不使用饱和色块整体填充**（现状四个语义色纯色块且无深色适配，是"整页先黑白灰"原则违反最严重处）。
单条 ≤ 2 行（须补 `line-clamp-2`），同屏 ≤ 3 条。
定位不得硬编码顶栏高度（现状 `top-[72px]` 耦合 `h-14`），改用 CSS 变量。

### 空状态

宽松层。24px 图标 + `title-3` 标题 + `body` 说明 + 至多一个主行动。
三种态（无数据/搜索中/无结果）必须视觉可区分，搜索中须有加载指示器——现状三态同形，仅文案不同。

### 骨架屏

必须与真实内容**逐像素等高**，数量按容器高度动态计算（现状写死 6 个且与真实卡片不等高，加载完成瞬间产生位移）。
色值随所在区域的色系，不得固定 gray。

## 12. 落地方式

### 12.1 Token 层

CSS 变量以**空格分隔的 RGB 通道**存储，使 Tailwind 的透明度修饰符（`bg-surface/50`）可用：

```css
:root      { --c-surface: 255 255 255; }
.dark      { --c-surface: 24 24 27; }
```

```js
// tailwind.config.js
colors: { surface: 'rgb(var(--c-surface) / <alpha-value>)' }
```

**[v2 更正]** 实际可用的类名如下（v1 写的 `text-text-secondary` / `border-border` 在配置里并不存在，
而 Tailwind 对不存在的类**静默不生成也不报错**，照抄会得到完全无样式的元素，
`typecheck` 和测试都发现不了）：

| 用途 | 类名 |
|---|---|
| 页面底 / 侧栏 / hover 底 | `bg-canvas` `bg-subtle` `bg-muted` |
| 卡片 / 浮层 | `bg-surface` `bg-raised` |
| 交互反馈 | `hover:bg-hover` `active:bg-active` |
| 文本四级 | `text-ink` `text-ink-secondary` `text-ink-tertiary` `text-ink-disabled` |
| 边框 | `border-line`（分隔）`border-control`（控件） |
| 主色 | `bg-accent` `text-accent` `text-accent-fg` |
| 功能色 | `text-success` `text-warning` `text-danger` |

**深色模式自动生效，不再需要 `dark:` 前缀**——这是消除现存 1178 处 `dark:` 的关键。

### 12.2 迁移路径

按此顺序执行，每步可独立验证、独立回滚：

0. **[v2 新增，提到最前] 移除 Markdown 主题的 Google Fonts `@import`。**
   这是全套迁移里唯一**零风险且零视觉变化**的改动——该 `@import` 从未成功过（全仓无 `@font-face`、
   无本地字体文件），删掉后渲染结果完全不变。v1 把它排在第 7 步是错的。
   同时补 `color-scheme`（修复深色下原生控件仍按浅色绘制）与 Electron `BrowserWindow.backgroundColor`
   （现状默认白底，深色模式启动时先闪一下白屏）。
1. **接入 token 层**（新增变量 + Tailwind 扩展）。此步除字体栈外零视觉变化。
2. **统一中性色**：`gray-*` → `zinc-*`。**[v2] 这一步不是纯机械替换**：
   `gray-*` 与 `zinc-*` 明度不同（如 `gray-500 #6b7280` vs `zinc-500 #71717a`），
   逐类替换会带来轻微色偏；更重要的是要同时处理 `MessageBubble.vue` 内嵌样式表里的
   **字面色值**（如代码块 `#1e1e2e`），它们抓不到、也不受 Tailwind 类替换影响。
3. **基础组件收敛**：按钮、输入框、徽章、弹窗骨架 —— 影响面最大、收益最高。
4. **焦点与层级**：补齐 focus-visible、统一 z-index 与遮罩。**此步修复可达性缺陷，优先级高于视觉。**
5. **按页重构**：笔记本 → 对话 → 个人中心 → 帮助。建议**笔记本先行**，它同时含列表与阅读两种区域，最能验证密度分层模型。
6. **色值 → token 替换**：`zinc-*` → 语义 token，消除 `dark:` 前缀。
7. **Markdown 主题重设计**：按附录的退化分级，为重度/中度依赖的 4 套主题重新调参。
   （移除 `@import` 本身已在第 0 步完成，此处只做视觉重设计。**[v2]** v1 在此处重复列了移除动作。）

第 1 步与第 4 步应优先于视觉改造——前者是基础设施，后者是缺陷修复。

- 密度验收（§2.2）不倒退
- 新增交互元素有 focus-visible
- 无新增 `dark:` 前缀（改用 token）
- 无新增非档位间距值
